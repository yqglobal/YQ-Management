# 1. At a Glance

Qmova is a cloud-based, multi-tenant Visit Management Platform.

The platform is designed around a single operational concept: the **Visit**.

A Visit may originate from an Appointment, Walk-in, Queue, Referral, or Staff-created workflow and can be tracked through its lifecycle until completion.

At a high level:

```text
Visitor
   │
   ▼
Customer Experience
(Appointment / Walk-in / Queue / QR Check-in)
   │
   ▼
Qmova Application
   │
   ├── Authentication
   ├── Authorization
   ├── Visit Management
   ├── Appointment Scheduling
   ├── Queue Management
   ├── Notifications
   ├── Analytics
   └── Audit Logging
   │
   ├──────────────┬───────────────┐
   ▼              ▼               ▼
PostgreSQL      Redis       External Services
                                   │
                         ┌─────────┴─────────┐
                         ▼                   ▼
                      Brevo             WhatsApp
```

Qmova is designed with the following architectural principles:

* Customers operate within logically isolated Workspaces.
* Authentication and authorization are separated.
* PostgreSQL provides persistent application data storage.
* Redis supports transient and real-time operational state where required.
* Socket.IO supports real-time application communication.
* Third-party services are used for selected capabilities such as authentication, email, and WhatsApp connectivity.
* Customers connect their own WhatsApp infrastructure.
* Qmova does not use a shared Qmova-owned WhatsApp identity to send customer messages.
* Security, auditability, and tenant isolation are considered throughout the application architecture.

# 3. What Qmova Is

Qmova is a **Visit Management Platform** for organizations that manage physical or scheduled interactions with people.

The platform combines workflows that are often handled independently, including:

* Appointment Scheduling;
* Walk-in management;
* Queue management;
* QR Check-in;
* Visit tracking;
* notifications;
* staff workflows; and
* analytics.

Qmova uses a **Visit-centric architecture**.

Rather than treating appointments, queues, and walk-ins as completely separate operational systems, they can represent different ways in which a Visit enters and progresses through the platform.

This allows Qmova to support a range of operating models while maintaining a common underlying Visit Lifecycle.

# 5. Core Platform Components

## 5.1 Frontend

The Qmova web application uses:

* Next.js 15
* TypeScript
* Tailwind CSS
* shadcn/ui

The frontend provides the user-facing experience for Customer administrators, Staff Members, and Visitors interacting with supported Qmova workflows.

Typical frontend responsibilities include:

* presenting authenticated Workspace interfaces;
* collecting form input;
* displaying Visits and queues;
* presenting Appointment information;
* handling QR Check-in experiences;

* managing account and Workspace settings.

The frontend does not independently determine authorization.

Authorization decisions are enforced by the backend.

# 7. Visit-Centric Architecture

The Visit is a central abstraction within Qmova.

A Visit may be created through different entry paths.

For example:

```text
                     ┌── Appointment
                     │
                     ├── Walk-in
                     │
Visitor / Staff ─────┼── Queue
                     │
                     ├── Referral
                     │
                     └── Staff-created Visit
                              │
                              ▼
                         Visit Created
                              │
                              ▼
                       Visit Lifecycle
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
             Waiting       In Service     Completed
                │
                ▼
             Cancelled /
             No-show /
             Other configured state
```

The exact states and transitions available to a Customer may depend on Workspace configuration and product functionality.

This abstraction allows Appointment-based and Walk-in workflows to coexist within the same operational platform.

# 8. Multi-Tenant Architecture

Qmova operates as a multi-tenant SaaS platform.

A Customer's environment is referred to as a **Workspace**.

The term **Tenant** describes the logical isolation model used by the platform, while **Workspace** is the customer-facing product concept.

A simplified model is:

```text
Qmova Platform
│
├── Workspace A
│     ├── Users
│     ├── Services
│     ├── Visits
│     ├── Appointments
│     └── Operational Data
│
├── Workspace B
│     ├── Users
│     ├── Services
│     ├── Visits
│     ├── Appointments
│     └── Operational Data
│
└── Workspace C
      ├── Users
      ├── Services
      ├── Visits
      ├── Appointments
      └── Operational Data
```

The purpose of tenant isolation is to prevent users in one Workspace from accessing data belonging to another Workspace without appropriate authorization.

Tenant context is therefore an important part of request processing and access control.

# 11. Persistent Data Storage

Qmova uses PostgreSQL as its primary relational data store.

PostgreSQL is used for persistent application information such as, depending on the feature:

* user records;
* Workspace relationships;
* Services;
* Visits;
* Appointments;
* configuration;
* audit records;
* policy records;
* consent records;
* other application data.

Qmova uses Prisma as the application data-access layer for PostgreSQL.

The database schema is designed around the platform's multi-tenant and relational data model.

---

# 12. Redis

Qmova uses Redis for operational workloads that benefit from low-latency, transient, or rapidly changing state.

Depending on the feature, Redis may support:

* queue state;
* caching;
* temporary application state;
* coordination;
* rate limiting;
* real-time operational workloads.

Redis should not be assumed to be the authoritative long-term source for every application record.

Persistent information that must survive transient infrastructure events is maintained through the appropriate persistent storage mechanism.

---

# 13. Real-Time Communication

Qmova uses Socket.IO to support real-time application updates.

Real-time communication can be used for workflows where users need current operational state without repeatedly refreshing the page.

Examples may include:

* queue position changes;
* Visit status updates;
* staff workflow changes;
* appointment state changes;
* live operational dashboards.

The backend remains the authoritative source for business rules and authorization.

Real-time channels do not independently grant a user access to another Workspace's data.

---

# 14. Authentication Architecture

Qmova supports multiple authentication methods.

These currently include:

* Google OAuth;
* email authentication; and
* OTP-based authentication.

Authentication answers:

> "Who is this user?"

Authorization answers:

> "What is this authenticated user allowed to access?"

Qmova treats these as separate concerns.

---

# 15. Google OAuth

When a user chooses Google authentication, Qmova relies on Google's OAuth authentication mechanisms to authenticate the user.

Qmova is designed to request only the information and permissions necessary to support account authentication and associated account functionality.

Depending on the authentication flow and provider response, information may include:

* name;
* email address;
* profile information;
* provider-specific user identifier.

OAuth credentials and tokens are treated as authentication material and are not intended to be exposed through ordinary Customer-facing application interfaces.

Users can discontinue use of Google authentication by using another supported authentication method where available and by following the applicable account-management process.

Google operates independently of Qmova and its own privacy and security practices apply to Google's handling of information.

# 19. Appointment Architecture

An Appointment represents a scheduled Visit.

Customers may configure appointment workflows according to their operating requirements.

Appointment functionality may include:

* scheduling;
* service selection;
* customer information;
* appointment status;
* reminders;
* arrival;
* check-in;
* queue participation where applicable;
* completion or cancellation.

Appointments and Walk-ins can ultimately enter the common Visit Lifecycle.

This allows a Customer to operate a combined appointment and queue model without requiring completely separate customer records for each workflow.

# 20. Queue Architecture

A Queue represents an ordered operational flow of waiting Visits.

Depending on Customer configuration, Queue behavior may involve:

* arrival time;
* service requirements;
* appointment status;
* priority;
* staff availability;
* business rules;
* operational state.

Qmova's Queue functionality is designed to support real-world Visit operations rather than assuming every Customer follows a single fixed first-in-first-out model.

The exact queue rules available to a Customer depend on the product functionality and configuration provided by Qmova.

# 23. Customer-Owned WhatsApp Architecture

WhatsApp is treated differently from Qmova's core application infrastructure because the messaging identity belongs to the Customer.

The conceptual relationship is:

```text
Customer
 │
 │ Owns
 ▼
WhatsApp Number / Account
 │
 │ Customer authorizes connection
 ▼
Evolution API Integration
 │
 ▼
Qmova Messaging Workflow
 │
 ├── Appointment Notification
 ├── Queue Notification
 ├── Visit Update
 └── Other Customer-configured Message
```

Qmova does not own the Customer's WhatsApp number.

Qmova does not become the owner of the Customer's WhatsApp conversations merely because Qmova provides integration infrastructure.

The Customer remains responsible for:

* its WhatsApp account;
* its recipients;
* its messaging purposes;
* applicable consents and notices;
* message content;
* compliance with applicable WhatsApp requirements.

Qmova provides the software infrastructure required to connect supported messaging workflows.

# 26. Data Boundaries

Qmova's architecture contains multiple logical trust boundaries.

At a high level:

```text
Visitor / User
      │
      ▼
Qmova Frontend
      │
      ▼
Qmova Backend
      │
      ├──────────────► Workspace Authorization
      │
      ├──────────────► Business Logic
      │
      ▼
Persistent / Operational Data
      │
      ├──────────────► PostgreSQL
      │
      └──────────────► Redis
      │
      ▼
External Providers
```

The most important boundary for Customer data is between one Workspace and another.

A user authenticated to one Workspace should not receive access to another Workspace's data solely because both Workspaces operate on the same Qmova platform.

# 31. Security Architecture Principles

Qmova's architecture is guided by the following principles.

## Least Privilege

Users and internal systems should receive only the access required for their function.

## Separation of Authentication and Authorization

Successfully identifying a user does not by itself grant access to all platform resources.

## Tenant Isolation

Workspace boundaries should be enforced at the application and authorization layers.

## Defense in Depth

Security should not depend on a single control.

## Auditability

Relevant security and administrative events should be observable through appropriate logs and audit records.

## Secure Defaults

Where practical, system defaults should minimize unnecessary exposure or access.

## Data Minimization

Qmova should avoid collecting or retaining information that is not necessary for the applicable product or operational purpose.
