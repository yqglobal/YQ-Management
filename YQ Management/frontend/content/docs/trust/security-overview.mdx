# 1. At a Glance

Security is a foundational part of Qmova's architecture and operating model.

Qmova is a multi-tenant Visit Management Platform that processes information on behalf of organizations managing customer Visits, Appointments, Walk-ins, Queues, QR Check-ins, Notifications, and related workflows.

Our security approach is based on:

* **Authentication** to establish the identity of users.
* **Authorization** to determine what authenticated users are permitted to access.
* **Role-Based Access Control (RBAC)** to limit access according to responsibilities.
* **Tenant isolation** to separate Customer Workspaces.
* **Encryption in transit** using secure network connections.
* **Audit logging** for relevant administrative and security events.
* **Session and account controls** to manage authenticated access.
* **Monitoring and operational logging** to identify failures and suspicious activity.
* **Backup and recovery practices** to support resilience.
* **Responsible disclosure** to provide a channel for reporting potential vulnerabilities.

Qmova does not claim that security risk can be eliminated completely.

Our controls, processes, and documentation are continuously evaluated and improved as the platform evolves.

# 2. Our Security Approach

Qmova's security model is designed around defense in depth.

Rather than relying on a single security mechanism, the platform uses multiple layers of controls across:

* identity;
* authorization;
* application logic;
* tenant boundaries;
* data storage;
* infrastructure;
* logging;
* monitoring;
* operational processes.

A simplified security model is:

```text id="7o8l8m"
Identity
   │
   ▼
Authentication
   │
   ▼
Workspace Context
   │
   ▼
Authorization / RBAC
   │
   ▼
Application Validation
   │
   ▼
Business Logic
   │
   ▼
Protected Data
   │
   ├── Audit Logging
   ├── Monitoring
   └── Operational Controls
```

No single layer is expected to provide complete protection by itself.

# 3. Security Principles

Qmova's security practices are guided by the following principles.

## Least Privilege

Access should be limited to what a user, system, or process needs to perform its intended function.

## Defense in Depth

Multiple independent or complementary controls should protect important systems and information.

## Tenant Isolation

Customer Workspaces must be logically separated so that authorized access in one Workspace does not automatically provide access to another.

## Secure Authentication

Authentication mechanisms should protect account access while collecting only the information necessary for the relevant workflow.

## Authorization at the Server

Security-sensitive authorization decisions must not depend solely on frontend behavior.

## Auditability

Important administrative and security events should be observable through appropriate logs and records.

## Data Minimization

The platform should avoid unnecessary collection and retention of personal information.

## Continuous Improvement

Security controls and processes should evolve as Qmova, its infrastructure, and its threat environment evolve.

# 4. Application Security

Qmova is built using a modern web application architecture that separates the customer-facing frontend from the backend application layer.

The current application stack includes:

**Frontend**

* Next.js 15
* TypeScript
* Tailwind CSS
* shadcn/ui

**Backend**

* NestJS
* Prisma
* PostgreSQL
* Redis
* Socket.IO

The backend is the primary enforcement point for:

* authentication;
* authorization;
* request validation;
* business rules;
* data access;
* integration logic.

Frontend interfaces are not treated as security boundaries by themselves.

A user being unable to see a button in the interface should not be relied upon as the only mechanism preventing access to the underlying operation.

# 6. Authorization and Role-Based Access Control

Authentication answers:

> Who is this user?

Authorization answers:

> What is this user allowed to do?

Qmova uses Role-Based Access Control (RBAC) to apply permissions within Customer Workspaces.

A simplified model is:

```text id="q1ur1s"
Authenticated User
        │
        ▼
Workspace Membership
        │
        ▼
Role
        │
        ▼
Permissions
        │
        ▼
Resource / Action
```

Authorization may apply to:

* Workspace administration;
* Staff management;
* Services;
* Visits;
* Appointments;
* Queues;
* analytics;
* integrations;
* account settings;
* other protected resources.

Customers are responsible for assigning appropriate roles to their users.

# 7. Tenant Isolation

Qmova operates as a multi-tenant SaaS platform.

Each Customer operates within a logically isolated Workspace.

Tenant isolation is a fundamental security requirement because multiple Customers share the same underlying application platform.

The application therefore uses Workspace context and authorization checks when processing protected resources.

Conceptually:

```text id="xyd6ab"
Request
   │
   ▼
Authenticated User
   │
   ▼
Workspace Context
   │
   ▼
Authorization Check
   │
   ▼
Requested Resource
```

A user authorized to access one Workspace should not be able to access another Workspace's data simply because both Workspaces operate on Qmova.

# 8. Data Protection

Qmova uses technical and organizational measures intended to protect information against unauthorized access, alteration, disclosure, loss, and misuse.

## Encryption in Transit

Connections to Qmova services are intended to use HTTPS/TLS or equivalent secure transport mechanisms.

This helps protect information while it moves between users, applications, and supported services.

## Protection of Credentials

Authentication credentials and other sensitive authentication material are not intended to be exposed through ordinary Customer-facing interfaces.

Where passwords are used, they are not stored in plain text.

## Data Minimization

Qmova is designed to avoid requiring information that is not necessary for the relevant service.

Customers remain responsible for determining what information they collect through their own Workspaces.

# 10. Session and Account Security

# 16. QR Check-in Security

Qmova supports QR-based Check-in workflows.

A QR code may direct a Visitor to a Customer-controlled Qmova check-in experience.

QR Check-in is designed to provide access to an intended workflow, not administrative privileges.

For example, scanning a Customer's check-in QR code should not by itself provide access to:

* Customer administration;
* Staff functions;
* analytics;
* private Workspace information;
* privileged APIs.

Customers should treat publicly displayed QR codes as public entry points and configure the associated workflow accordingly.

# 17. Customer-Owned WhatsApp Security Model

Qmova uses a customer-owned model for WhatsApp connectivity.

The architecture is intentionally different from a model where a SaaS provider sends every customer's messages from one platform-owned WhatsApp identity.

The conceptual flow is:

```text id="z7qd77"
Customer
   │
   ▼
Customer-owned WhatsApp
   │
   ▼
Customer-authorized connection
   │
   ▼
Evolution API
   │
   ▼
Qmova Messaging Workflow
```

Under this model:

* Customers own their WhatsApp numbers.
* Customers control their connected WhatsApp environment.
* Qmova does not own Customer WhatsApp numbers.
* Qmova does not use a Qmova-owned WhatsApp identity as the Customer's sender.
* Customers remain responsible for their WhatsApp account and message content.
* Customers are responsible for complying with applicable messaging requirements and third-party policies.

Qmova provides infrastructure supporting the integration.

Third-party messaging infrastructure remains subject to its own security and privacy controls.

# 19. Backup and Recovery

Backups are an important component of Qmova's resilience strategy.

Backup practices are intended to support recovery from situations such as:

* accidental data deletion;
* infrastructure failures;
* operational mistakes;
* certain security incidents.

Backup copies may persist for a limited period after data has been removed from primary production systems.

This is a normal characteristic of backup systems and does not necessarily indicate that deleted information remains actively available through the Qmova application.

Recovery procedures are reviewed and improved as the platform matures.

Specific service-level recovery commitments, if applicable, are governed by the relevant Customer agreement or Service Level Agreement.

# 25. Security and Privacy Relationship

Security and privacy address different questions.

**Privacy** asks:

> Why is information collected and how should it be used?

**Security** asks:

> How is information protected against unauthorized access, loss, or misuse?

Qmova addresses both through complementary controls and documentation.

The Privacy Policy explains how Qmova processes personal information.

The Security Policy explains Qmova's security practices in greater detail.

The Data Processing Addendum addresses contractual data-processing obligations for applicable Customer relationships.
