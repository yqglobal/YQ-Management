# 1. At a Glance

Qmova is a multi-tenant Visit Management Platform that processes information on behalf of organizations managing customer Visits, Appointments, Walk-ins, Queues, QR Check-ins, Notifications, and related workflows.

Our security program is based on layered controls rather than a single security mechanism.

Key areas include:

* authenticated access;
* Role-Based Access Control;
* Workspace and Tenant isolation;
* secure application architecture;
* encryption in transit;
* credential protection;
* audit logging;
* security monitoring;
* vulnerability management;
* backup and recovery;
* incident response;
* third-party risk management;
* responsible disclosure.

Qmova does **not** currently claim SOC 2, ISO 27001, HIPAA, or other security certifications unless specifically identified in an applicable Qmova document or agreement.

This Security Policy describes Qmova's current security framework at a high level. Specific implementation details may change as the platform evolves.

# 3. Security Principles

Qmova's security program is guided by the following principles.

## Least Privilege

Access is limited to the minimum permissions needed to perform an authorized function.

## Defense in Depth

Security relies on multiple protective layers rather than one control.

## Tenant Isolation

Customer Workspaces must remain logically separated from one another.

## Secure by Design

Security requirements are considered as part of application and infrastructure design rather than only after deployment.

## Accountability

Relevant security and administrative activity should be observable through appropriate logging and audit mechanisms.

## Data Minimization

Qmova should avoid collecting or retaining information that is unnecessary for the applicable purpose.

## Continuous Improvement

Security controls are reviewed and improved as Qmova, its architecture, and the threat environment evolve.

# 7. Identity and Authentication

Qmova uses authentication controls to verify the identity of Users.

Supported authentication mechanisms include:

* Google OAuth;
* email authentication;
* OTP-based authentication.

Authentication is separate from authorization.

A successfully authenticated User is not automatically entitled to access every Qmova resource.

Authentication-related events may be logged for security, auditing, and operational purposes.

Qmova does not intentionally store passwords in plain text.

---

# 8. Authorization and Access Control

Qmova uses server-side authorization and Role-Based Access Control (RBAC) to control access to protected resources.

A simplified authorization flow is:

```text id="k7tv3s"
User
  │
  ▼
Authentication
  │
  ▼
Workspace Membership
  │
  ▼
Role
  │
  ▼
Permissions
  │
  ▼
Requested Resource
```

Authorization may be applied to:

* Workspace settings;
* Visits;
* Appointments;
* Queues;
* Services;
* Staff Members;
* analytics;
* integrations;
* administrative functions.

The frontend is not considered a sufficient authorization boundary on its own.

Security-sensitive authorization decisions must be enforced on the server.

---

# 9. Tenant Isolation

Qmova is a multi-tenant SaaS platform.

Customer environments are represented as Workspaces.

Tenant isolation is intended to prevent unauthorized access between different Customer environments.

The application uses Workspace and User context to determine whether a request may access a particular resource.

A User authorized within Workspace A should not gain access to Workspace B merely because both Workspaces use the same Qmova platform.

Tenant isolation applies to relevant:

* application data;
* APIs;
* operational resources;
* real-time events;
* administrative functions.

# 12. Secrets and Credential Management

Credentials and secrets used by Qmova systems are treated as sensitive information.

Examples include:

* API keys;
* OAuth secrets;
* database credentials;
* service credentials;
* signing secrets;
* integration credentials.

Qmova's security practices are designed to:

* avoid exposing secrets through public interfaces;
* restrict access to authorized systems and personnel;
* avoid storing secrets in ordinary source-code locations;
* rotate credentials where appropriate;
* revoke compromised credentials when identified.

Sensitive credentials must not be included in public repositories, documentation, support communications, or customer-facing interfaces.

# 17. Real-Time Communication Security

Qmova uses Socket.IO to support selected real-time functionality.

Real-time functionality may support:

* Queue updates;
* Visit status;
* operational dashboards;
* other live application state.

Authorization remains applicable to real-time communication.

A real-time connection must not be treated as an independent authorization mechanism.

Qmova aims to ensure that Users receive only events appropriate to their authenticated Workspace and permissions.

# 18. QR Check-in Security

QR Check-in allows Visitors to access a designated Customer workflow.

QR codes are intended as public entry points rather than administrative credentials.

A QR code should not provide:

* Workspace administration;
* Staff permissions;
* unrestricted data access;
* privileged API access.

Customers should treat publicly displayed QR codes as discoverable information and configure associated workflows accordingly.

---

# 19. Messaging and WhatsApp Security

Qmova uses a Customer-owned architecture for supported WhatsApp workflows.

The Customer:

* owns the WhatsApp number;
* controls the WhatsApp environment;
* authorizes its connection;
* controls message content.

Qmova:

* provides integration infrastructure;
* processes the information necessary to support the workflow;
* does not own Customer WhatsApp numbers;
* does not use a shared Qmova-owned WhatsApp identity for Customer messages.

The Customer remains responsible for:

* account security;
* messaging permissions;
* recipients;
* message content;
* applicable messaging rules.

Qmova may restrict an integration where necessary to address security threats, abuse, legal requirements, or provider restrictions.

# 40. Responsible Disclosure

Qmova encourages responsible reporting of suspected vulnerabilities.

Security researchers and other parties should report potential vulnerabilities to:

**[security@qmova.com](mailto:security@qmova.com)**

Security testing must not:

* access another Customer's data;
* intentionally disrupt the Platform;
* destroy information;
* exfiltrate unnecessary data;
* perform denial-of-service attacks;
* compromise accounts;
* continue exploitation after sufficient evidence has been obtained.

The Qmova Responsible Disclosure Policy provides the detailed reporting and testing requirements.
